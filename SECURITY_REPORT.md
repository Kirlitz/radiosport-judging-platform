## V-01. Обход rate limiting через подделку X-Forwarded-For — **ИСПРАВЛЕНО**

**Статус (14.09.2026):** `_client_ip()` в `app/__init__.py` больше не доверяет первой записи XFF. XFF читается только при прямом соединении с доверенным прокси (`TRUSTED_PROXY_IPS`, по умолчанию `127.0.0.1, ::1`) и берётся последняя запись заголовка (её добавляет сам nginx). Прямые соединения из интернета используют IP соединения, XFF игнорируется. Проверено тестовым клиентом: подделка заголовка не меняет ключ лимита.
**Условие:** gunicorn должен слушать только `127.0.0.1`, наружу — только порт nginx.

**Где:** `app/__init__.py:11-17`

```python
def _client_ip():
    xff = request.headers.get('X-Forwarded-For')
    if xff:
        return xff.split(',')[0].strip()   # берётся ПЕРВАЯ запись
    return get_remote_address()
limiter = Limiter(key_func=_client_ip)
```

**Описание.** Ключ rate limit строится от первой записи заголовка `X-Forwarded-For`, который полностью контролируется клиентом:

1. За стандартным nginx (`proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`) заголовок имеет вид `<заведённый клиентом>, <реальный IP>` — первая запись управляется атакующим.
2. Без прокси (run.py слушает `0.0.0.0:5000`) клиент присылает XFF напрямую — лимиты вообще не срабатывают.

**Влияние.**
- Безлимитный брутфорс `/admin/login` (лимит «5 per 15 minutes» обнуляется каждой новой поддельной XFF). Логин `admin` предсказуем (подтверждено в БД), пароль защищён только scrypt-хэшем — онлайн-перебор становится возможен.
- Обход лимитов `/upload` (10/мин) и `/confirm` (15/мин) → массовая генерация записей PendingUpload (до 5 МБ raw_text в SQLite) и файлов на диске → исчерпание диска/БД (DoS).

**PoC (схема):**
```
POST /admin/login HTTP/1.1
X-Forwarded-For: 203.0.113.<случайное>
```
Каждый запрос — новый «IP» → лимит 5/15 мин никогда не срабатывает.

**Рекомендации.**
- Не доверять первой записи XFF. Варианты:
  - nginx: `proxy_set_header X-Forwarded-For $remote_addr;` (перезапись, а не append) + оставить `get_remote_address()`;
  - либо в flask-limiter: `Limiter(key_func=get_remote_address, default_limits=[...])` + правильная настройка `PROXY_COUNT`/доверенных прокси;
  - либо валидировать XFF: доверять только последней записи, добавленной доверенным прокси.
- Дополнительно: учсть, что при нескольких воркерах in-memory лимиты и так ослаблены (V-05).

## V-02. Cookie сессии без флага Secure — **ИСПРАВЛЕНО**

**Статус (14.09.2026):** в `config.py` явно заданы `SESSION_COOKIE_SECURE` (по умолчанию `1`, для локальной разработки — `SESSION_COOKIE_SECURE=0`), `SESSION_COOKIE_HTTPONLY=True`, `SESSION_COOKIE_SAMESITE='Lax'`. Проверено тестовым клиентом: `Set-Cookie: session=...; Secure; HttpOnly; Path=/; SameSite=Lax`.

**Где:** `config.py`

**Описание.** `SESSION_COOKIE_SECURE` не установлен (default `False`), `SESSION_COOKIE_HTTPONLY=True` и `SESSION_COOKIE_SAMESITE='Lax'` — по умолчанию Flask. Сессия администратора (`admin_logged=True`) передаётся по обычному HTTP, если сайт доступен не только через TLS.

**Влияние.** Перехват сессионной cookie при передаче по незащищённому каналу (Wi-Fi, провайдер) → полная компрометация админ-панели (удаление соревнований/файлов, подмена результатов).

**Рекомендации.**
- `SESSION_COOKIE_SECURE = True` (в production, за TLS-терминацией nginx — учитывать `X-Forwarded-Proto` / `PREFERRED_URL_SCHEME`),
- включить HSTS (см. V-04),
- при смене пароля/удалении аккаунта принудительно разлогинивать сессии (сейчас флаг `admin_logged` живёт до закрытия браузера).

## V-03. Лишний админ-аккаунт `ua0lid` в БД — **СРЕДНЯЯ**

**Где:** `data/judging.db`, таблица `admin`

**Описание.** В базе обнаружено два администратора: `admin` и `ua0lid` (оба с корректными scrypt-хэшами). Второй аккаунт выглядит как тестовый/остаточный (имя совпадает с позывным участника).

**Влияние.** Расширенная поверхность атаки: у каждого админа свой пароль; забытый/слабый пароль тестового аккаунта = вход в судейскую. Также затрудняет аудит «кто заходил».

**Рекомендации.** Удалить неиспользуемые аккаунты; вести учёт админ-аккаунтов; рассмотреть MFA для входа.

## V-04. Отсутствуют защитные HTTP-заголовки — **НИЗКАЯ**

**Где:** весь app (глобально)

**Описание.** Не заданы: `X-Frame-Options` / `CSP: frame-ancestors`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Strict-Transport-Security`.

**Влияние.** Страницу `/admin/login` (и админ-панель) можно встроить в iframe на вредоносном сайте (clickjacking: подманивание админа на клик по «Судить»/«Удалить»). Реальные POST-действия защищены CSRF-токенами, поэтому последствия ограничены, но классика кликджекинга работает.

**Рекомендации.** Добавить после каждого ответа (или в nginx):
```
X-Content-Type-Options: nosniff
Referrer-Policy: same-origin
Content-Security-Policy: frame-ancestors 'none'
Strict-Transport-Security: max-age=31536000; includeSubDomains (за TLS)
```

## V-05. In-memory хранилище rate limit — **НИЗКАЯ**

**Где:** `app/__init__.py:31` (`RATELIMIT_STORAGE_URI = "memory://"`)

**Описание.** Счётчики хранятся отдельно в каждом воркере. При рекомендуемом запуске `gunicorn -w 3` фактический лимит ×3 (15 попыток/15 мин на логин), при рестарте воркера счётчики обнуляются.

**Рекомендации.** Для production — `redis://` (`RATELIMIT_STORAGE_URI`).

## V-06. Stored XSS в admin_edit.html (само-XSS администратора) — **НИЗКАЯ**

**Где:** `app/templates/admin_edit.html:116-160`

**Описание.** JavaScript строит DOM через `innerHTML`, подставляя значения из БД с экранированием только двойных кавычек:

```js
row.innerHTML = `<input ... value="${value.replace(/"/g, '&quot;')}" ...>`;
```

Если админ создаст зачётную группу с именем, например `"><img src=x onerror=alert(1)>`, при открытии `/admin/edit/<id>` выполнится произвольный JS.

**Влияние.** Только админ может записать такие категории/туры → само-XSS; реальный риск — если админ скопирует вредоносную строку из недоверенного источника (чат/почта). Кража сессии админа теоретически возможна.

**Рекомендации.** Не собирать HTML через `innerHTML` с внешними значениями: использовать `document.createElement` + `el.value = value`, либо экранировать HTML-спецсимволы (`<`, `>`, `&`, `'`) на JS-стороне.

## V-07. Имя плагина судейства не валидируется — **НИЗКАЯ**

**Где:** `app/routes/admin.py:181,225,321`

**Описание.** `scoring_script_filename` сохраняется из формы без проверки по списку доступных плагинов и используется в `importlib.import_module(f'app.judging.{script_name}')`. Имя ограничено пакетом `app.judging` (префикс хардкодом), поэтому произвольный импорт модулей системы невозможен; запускать может только авторизованный админ. Тем не менее в БД можно записать имя несуществующего/чужого модуля, а при добавлении новых файлов в `app/judging/` любой админ сможет запускать их без контроля.

**Рекомендации.** При сохранении формы валидировать значение по возвращаемому `get_available_plugins()`; при запуске судейства — повторно проверять, что имя входит в список плагинов.

## V-08. DoS-потенциал (тяжёлые запросы, N+1) — **НИЗКАЯ**

**Где:**
- `app/judging/*.py` — кросс-чек выполняет по одному SQL-запросу на каждую валидную QSO (`QSO.query.filter(...).all()`), затем циклы по логам; при сотнях участников с тысячами связей судейство занимает минуты и блокирует воркер gunicorn (таймаута на запрос нет);
- `app/routes/user.py:29-38`, `app/routes/main.py:37-42` — N+1-запросы на каждой публичной странице (по запросу ReceivedLog на каждое соревнование);
- `app/templates/preview.html` — рендерит ВСЕ QSO загруженного файла (до 5 МБ текста) в одну HTML-страницу → многомегабайтный ответ и пиковое потребление памяти.

**Влияние.** Дegradation/недоступность при больших соревнованиях; усиливается обходом лимитов (V-01).

**Рекомендации.** Асинхронный запуск судейства (очередь/fork + статус), кэширование/пагинация списков, ограничение числа строк в превью.

## V-09. Dev-сервер на всех интерфейсах — **НИЗКАЯ**

**Где:** `run.py:8` — `app.run(host='0.0.0.0', port=5000)`

**Описание.** Если этот файл использовать в production (вместо gunicorn), наружу на все интерфейсы выставляется Werkzeug dev server (не рассчитан на production, плюс — см. V-01 — прямой доступ к XFF без прокси).

**Рекомендации.** В production запускать только через gunicorn за nginx; `host='0.0.0.0'` убрать из run.py (оставить 127.0.0.1 для разработки).

## V-10. Часовые пояса: local time vs UTC — **ИНФОРМАЦИЯ**

**Где:** `app/routes/user.py:54-58,185-186`, `app/judging/*.py`

**Описание.** Дедлайны (`datetime.now()`, локальное время сервера) сравниваются с UTC-временем QSO из Cabrillo-отчётов. Если TZ сервера не UTC — границы туров и дедлайны считаются с смещением (функциональная ошибка, влияет на корректность результатов, а не на безопасность напрямую).

**Рекомендации.** Использовать `datetime.now(timezone.utc)` везде, где сравниваются с временем из отчётов, либо явно фиксировать TZ в конфигурации.

## V-11. Сервисные скрипты и мёртвый код в production-копии — **ИНФОРМАЦИЯ**

- `new_pass.py` — интерактивно создаёт/сбрасывает пароль админа; не должен находиться в production (риск случайного/несанкционированного запуска с консоли сервера).
- `dump_project.py` — собирает весь исходник в один файл; при запуске на сервере может увезти исходный код.
- `app/templates/admin.html`, `app/templates/competition_form.html` — не используются (нет ссылок из кода). Удалить.
- `__pycache__/` и `data/judging.db` лежат в корне проекта — исключить из деплоя/бэкапа в открытом виде.

## V-12. Logout по GET — **ИНФОРМАЦИЯ**

**Где:** `app/routes/admin.py:146-149`

Ссылка-выход может быть инициирована через CSRF (загрузка картинки со стороннего сайта). Влияние минимальное (только разлогин), но правильнее — POST + CSRF-токен.

# Проверено, проблем не найдено

| Область | Результат |
|---------|-----------|
| **SQLi** | Отсутствует. Все запросы через SQLAlchemy ORM, параметры маршрутов типизированы (`<int:comp_id>`), `get_or_404`; raw SQL не используется. |
| **XSS (шаблоны)** | Отсутствует. Автоэкранирование Jinja активно, `|safe` / `Markup` / `mark_safe` в шаблонах нет (единственный риск — JS, см. V-06). |
| **SSTI** | Отсутствует. Имена шаблонов статические, пользовательский ввод в `render_template` не подставляется. |
| **CSRF** | `CSRFProtect` включён глобально, без исключений; все формы содержат `csrf_token`. |
| **Загрузка файлов** | Безопасная. Белосписок расширений `.cbr/.log/.txt`; файл сохраняется под серверным именем `secure_filename(<позывной>)_<id>.cbr`; хранилище `data/logs` — вне веб-корня и не сервируется; лимит 5 МБ. |
| **Path Traversal** | Отсутствует. Пути удаления/записи строятся из `secure_filename` и целочисленных ID; `file_path` в БД формируется только сервером. |
| **Zip Slip** | Отсутствует. `zipfile` используется только на запись (экспорт UBN), чтение архивов отсутствует. |
| **RCE / код-инъекции** | `exec`/`eval`/`subprocess`/`os.system`/`pickle`/`yaml.load` отсутствуют. Единственный динамический импорт — плагины в `app/judging` (см. V-07). |
| **Пароли** | Хэширование `scrypt:32768:8:1` (Werkzeug 3.x, default) — современный алгоритм; поле 255 символов. Ошибка логина без раскрытия существования пользователя. |
| **SECRET_KEY** | Берётся только из env, без fallback — приложение падает при отсутствии (правильно). |
| **Подмена отчёта (business logic)** | Реализовано корректно: одноразовый токен `secrets.token_urlsafe(32)`, серверная копия raw_text, проверка `competition_id`, TTL 30 мин, флаг `used`. Позывной — строгий regex `^[A-Z0-9/]{3,20}$`, проверка «чужих связей» в логе. |
| **Утечка данных в ответах** | 429-страница статическая; ошибки плагинов выводятся только администратору. |

# Общие рекомендации (приоритет)

1. **Срочно:** исправить ключ rate limit (V-01) — это главный вектор атаки на текущий момент.
2. Включить `SESSION_COOKIE_SECURE` + HSTS + заголовки (V-02, V-04).
3. Удалить аккаунт `ua0lid` (V-03).
4. Production: gunicorn за nginx (XFF перезаписывать), redis для лимитов (V-05, V-09).
5. Валидация имени плагина (V-07), убрать dev-скрипты и мёртвые шаблоны (V-11).
