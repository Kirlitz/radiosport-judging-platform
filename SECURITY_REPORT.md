## V-01. Обход rate limiting через подделку X-Forwarded-For — **ИСПРАВЛЕНО**

**Статус (14.09.2026):** `_client_ip()` в `app/__init__.py` больше не доверяет первой записи XFF. XFF читается только при прямом соединении с доверенным прокси (`TRUSTED_PROXY_IPS`, по умолчанию `127.0.0.1, ::1`) и берётся последняя запись заголовка (её добавляет сам nginx). Прямые соединения из интернета используют IP соединения, XFF игнорируется. Проверено тестовым клиентом: подделка заголовка не меняет ключ лимита.
**Условие:** gunicorn должен слушать только `127.0.0.1`, наружу — только порт nginx.

**Где:** `app/__init__.py:28`

```python
def _client_ip():
    xff = request.headers.get('X-Forwarded-For')
    if xff:
        return xff.split(',')[0].strip()   # берётся ПЕРВАЯ запись
    return get_remote_address()
limiter = Limiter(key_func=_client_ip)
```

**Описание.** Ключ rate limit строится от первой записи заголовка `X-Forwarded-For`, который полностью контролируется клиентом:

1. За стандартным nginx (`proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`) заголовок имеет вид `<заведённый клиентом>, <реальный IP>` — первая запись управляется атакующим.
2. Без прокси (run.py слушает `0.0.0.0:5000`) клиент присылает XFF напрямую — лимиты вообще не срабатывают.

**Влияние.**
- Безлимитный брутфорс `/admin/login` (лимит «5 per 15 minutes» обнуляется каждой новой поддельной XFF). Логин `admin` предсказуем (подтверждено в БД), пароль защищён только scrypt-хэшем — онлайн-перебор становится возможен.
- Обход лимитов `/upload` (10/мин) и `/confirm` (15/мин) → массовая генерация записей PendingUpload (до 5 МБ raw_text в SQLite) и файлов на диске → исчерпание диска/БД (DoS).

**PoC (схема):**
```
POST /admin/login HTTP/1.1
X-Forwarded-For: 203.0.113.<случайное>
```
Каждый запрос — новый «IP» → лимит 5/15 мин никогда не срабатывает.

## V-02. Cookie сессии без флага Secure — **ИСПРАВЛЕНО**

**Статус (14.09.2026):** в `config.py` явно заданы `SESSION_COOKIE_SECURE` (по умолчанию `1`, для локальной разработки — `SESSION_COOKIE_SECURE=0`), `SESSION_COOKIE_HTTPONLY=True`, `SESSION_COOKIE_SAMESITE='Lax'`. Проверено тестовым клиентом: `Set-Cookie: session=...; Secure; HttpOnly; Path=/; SameSite=Lax`.

**Статус (18.09.2026):** дополнительно:
- в production имя cookie меняется на `__Host-session` (требует `Secure`, `Path=/`, без `Domain`) — защита от перехвата cookie через поддомены/не-тёмный путь;
- реализована инвалидация сессий: сессия привязана к токену (sha256-хеш в БД `session_token_hash`), при смене пароля/деактивации аккаунта все сессии аннулируются (было в рекомендациях V-02).

**Где:** `config.py` (cookie), `app/auth.py:31-66` (токен сессии), `app/routes/admin.py:176-178` (инвалидация)

**Описание.** `SESSION_COOKIE_SECURE` не установлен (default `False`), `SESSION_COOKIE_HTTPONLY=True` и `SESSION_COOKIE_SAMESITE='Lax'` — по умолчанию Flask. Сессия администратора передаётся по обычному HTTP, если сайт доступен не только через TLS.

**Влияние.** Перехват сессионной cookie при передаче по незащищённому каналу (Wi-Fi, провайдер) → полная компрометация админ-панели.

## V-03. Лишний админ-аккаунт `ua0lid` в БД — **СРЕДНЯЯ**

**Где:** `data/judging.db`, таблица `admin`

**Описание.** В базе обнаружено два администратора: `admin` и `ua0lid` (оба с корректными scrypt-хэшами). Второй аккаунт выглядит как тестовый/остаточный (имя совпадает с позывным участника).

**Влияние.** Расширенная поверхность атаки: у каждого админа свой пароль; забытый/слабый пароль тестового аккаунта = вход в судейскую.

**Рекомендации.** Удалить аккаунт `ua0lid` вручную (код не трогается — это гигиена данных). Рассмотреть MFA для входа.

## V-04. Отсутствуют защитные HTTP-заголовки — **ИСПРАВЛЕНО**

**Статус (18.09.2026):** глобальный `@app.after_request` в `app/__init__.py:82-101` добавляет на все ответы:
`X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: same-origin`, `Content-Security-Policy` (`frame-ancestors 'none'; base-uri 'self'; form-action 'self'` и др.), `Permissions-Policy`, а при включённом Secure-флаге сессии — `Strict-Transport-Security: max-age=31536000; includeSubDomains`. Проверено тестовым клиентом.

**Где:** `app/__init__.py:82`

**Описание (до правки).** Не заданы: `X-Frame-Options` / `CSP: frame-ancestors`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Strict-Transport-Security`.

**Влияние (до правки).** Страницу `/admin/login` можно встроить в iframe на вредоносном сайте (clickjacking). Реальные POST-действия защищены CSRF-токенами, поэтому последствия ограничены.

## V-05. In-memory хранилище rate limit — **ИСПРАВЛЕНО**

**Статус (18.09.2026):** жёсткая строка `RATELIMIT_STORAGE_URI = "memory://"` в коде убрана; хранилище настраивается через переменную окружения `RATELIMIT_STORAGE_URI` (`config.py`, по умолчанию `memory://`).

**Где:** `config.py` (раньше `app/__init__.py:31`)

**Описание.** Счётчики хранятся отдельно в каждом воркере. При `gunicorn -w 3` фактический лимит ×3 (15 попыток/15 мин на логин), при рестарте воркера счётчики обнуляются.

**Рекомендации.** Для production указать общий `redis://` в `RATELIMIT_STORAGE_URI` (тогда лимиты одинаковы для всех воркеров).

## V-06. Stored XSS в admin_edit.html (само-XSS администратора) — **ИСПРАВЛЕНО**

**Статус (18.09.2026):** двойная защита:
- серверная валидация: в `_parse_competition_form` (`app/routes/admin.py:229`) туры принимаются только в формате `datetime-local` (`YYYY-MM-DDTHH:MM`) — произвольные строки в JSON туров не сохраняются;
- JS-экранирование: в `app/templates/admin_edit.html` добавлен `escHtml()` (`&`, `"`, `<`, `>`) для значений `start`/`end`/`divideBy`/`divideValue` туров.

**Где:** `app/templates/admin_edit.html` (ФС), `app/routes/admin.py:229`

**Описание (до правки).** JavaScript строит DOM через `innerHTML`, подставляя значения из БД с экранированием только двойных кавычек:

```js
row.innerHTML = `<input ... value="${value.replace(/"/g, '&quot;')}" ...>`;
```

Если админ создаст зачётную группу с именем, например `"><img src=x onerror=alert(1)>`, при открытии `/admin/edit/<id>` выполнится произвольный JS.

**Влияние (до правки).** Только админ может записать такие категории/туры → само-XSS; реальный риск — если админ скопирует вредоносную строку из недоверенного источника.

## V-07. Имя плагина судейства не валидируется — **ИСПРАВЛЕНО**

**Статус (18.09.2026):** добавлена `_validate_plugin()` (`app/routes/admin.py:57`): имя плагина принимается только если присутствует в `get_available_plugins()` (сканирование реальных файлов `app/judging/`). Применяется при создании и редактировании соревнования, а также повторно при запуске судейства. Недопустимое/несуществующее имя заменяется на доступный плагин (сначала `primorye_hf`, затем `judging`, иначе первый из доступных).

**Где:** `app/routes/admin.py:57, 290, 315, 452`

**Описание (до правки).** `scoring_script_filename` сохранялся из формы без проверки по списку доступных плагинов и использовался в `importlib.import_module(f'app.judging.{script_name}')`. Имя ограничено пакетом `app.judging` (префикс хардкодом), поэтому произвольный импорт модулей системы невозможен, но в БД можно было записать имя несуществующего/чужого модуля, а при добавлении новых файлов в `app/judging/` любой админ мог бы запускать их без контроля.

## V-08. DoS-потенциал (тяжёлые запросы, N+1) — **ЧАСТИЧНО ИСПРАВЛЕНО**

**Статус (18.09.2026):** ограничено превью отчёта: рендерится не более `PREVIEW_MAX_QSO = 1000` связей (`app/routes/user.py`), итоговое судейство идёт по полной серверной копии отчёта; в `preview.html` добавлено предупреждение о усечении. - кросс-чек в `app/judging/*.py` — по одному SQL-запросу на каждую валидную QSO, судейство без таймаута блокирует воркер gunicorn;

**Рекомендации (остаток).** Асинхронный запуск судейства (очередь/fork + статус), кэширование/пагинация списков.

## V-10. Часовые пояса: local time vs UTC — **ОТКРЫТО**

**Где:** `app/routes/user.py`, `app/judging/*.py`

**Описание.** Дедлайны (`datetime.now()`, локальное время сервера) сравниваются с UTC-временем QSO из Cabrillo-отчётов. Если TZ сервера не UTC — границы туров и дедлайны считаются с смещением (функциональная ошибка, влияет на корректность результатов, а не на безопасность напрямую).

**Рекомендации.** Использовать `datetime.now(timezone.utc)` везде, где сравниваются с временем из отчётов, либо явно фиксировать TZ в конфигурации.

# Повторный аудит 18.09.2026: новые находки и правки

## F-01. Excel formula injection (CWE-1236) — **ИСПРАВЛЕНО**

**Статус (18.09.2026):** добавлена `_excel_safe()` (`app/routes/admin.py:78`): строковые значения, начинающиеся с `=`, `+`, `-`, `@`, получают префикс `'` (ячейка Excel интерпретируется как текст, формула не выполняется). Применяется ко всем строковым колонкам выгрузки `export_excel` (позывной, ФИО, год, разряд, регион). Проверено тестовым клиентом: ячейка со значением `=1+1` в сгенерированном .xlsx имеет `data_type='t'` (строка `'=1+1`), сырые формулы отсутствуют.

**Где:** `app/routes/admin.py:78, 550-560`

**Описание.** `export_excel` (до ~520 строки) писал значения из БД напрямую в openpyxl. Экспериментально подтверждено: openpyxl хранит строки, начинающиеся с `=`, как формулы (`data_type='f'`). Пользователь мог загрузить отчёт, где позывной/ФИО/регион начинаются с `=HYPERLINK(...)`, `=1+1` и т.п.; при открытии экспортированного файла в Excel эти ячейки выполнялись.

**Влияние.** Офисная малварь/фишинг через сгенерированных файл результатов (загрузка из-под доверенного домена, запуск формул в режиме макрос-подобного поведения) — устаревшие Excel могут выполнять DDE-команды. Критичность повышается тем, что экспорт доступен только авторизованным администраторам, но значения в файл попадают от недоверенных участников (их заявки).

## F-04. Rate limit логина только по IP — **ИСПРАВЛЕНО**

**Статус (18.09.2026):** на `/admin/login` добавлен второй лимитер `@limiter.limit("8 per 15 minutes", key_func=_login_bucket_key, methods=["POST"])` (`app/routes/admin.py:169-186`), где ключ — пара `IP|логин` (нормализованный к нижнему регистру). Существующий общий лимит «5 per 15 minutes» по IP сохранён.

**Описание.** До правки лимит был только на IP: медленный распределённый перебор одного логина (`admin`) с разных IP или с одного IP с ротацией прокси обходил защиту, а «5 на IP» легко добивается легитимными кликами за NAT.

**Влияние (было).** Подбор слабого пароля админа в долгосрочной перспективе без шумов в логах.

# Проверено, проблем не найдено

| Область | Результат |
|---------|-----------|
| **SQLi** | Отсутствует. Все запросы через SQLAlchemy ORM, параметры маршрутов типизированы (`<int:comp_id>`), `get_or_404`; raw SQL не используется. |
| **XSS (шаблоны)** | Отсутствует. Автоэкранирование Jinja активно, `|safe` / `Markup` / `mark_safe` в шаблонах нет (риск был только в JS админ-формы, исправлен — см. V-06). |
| **SSTI** | Отсутствует. Имена шаблонов статические, пользовательский ввод в `render_template` не подставляется. |
| **CSRF** | `CSRFProtect` включён глобально, без исключений; все формы содержат `csrf_token`. Проверено: POST без токена → 400. |
| **Загрузка файлов** | Безопасная. Белосписок расширений `.cbr/.log/.txt`; файл сохраняется под серверным именем `secure_filename(<позывной>)_<id>.cbr`; хранилище `data/logs` — вне веб-корня и не сервируется; лимит 5 МБ. |
| **Path Traversal** | Отсутствует. Пути удаления/записи строятся из `secure_filename` и целочисленных ID; `file_path` в БД формируется только сервером. |
| **Zip Slip** | Отсутствует. `zipfile` используется только на запись (экспорт UBN), чтение архивов отсутствует. |
| **RCE / код-инъекции** | `exec`/`eval`/`subprocess`/`os.system`/`pickle`/`yaml.load` отсутствуют. Единственный динамический импорт — плагины в `app/judging`, имя валидируется по белому списку (V-07). |
| **Пароли** | Хэширование `scrypt:32768:8:1` (Werkzeug 3.x, default) — современный алгоритм; поле 255 символов. Ошибка логина не раскрывает существование пользователя (заглушка-хэш). |
| **SECRET_KEY** | Берётся только из env, без fallback — приложение падает при отсутствии (правильно). |
| **Экспорт в Excel** | Formula injection нейтрализована `_excel_safe()` (F-01). Проверено: значения `=1+1`, `@X` экспортируются как текст. |
| **Сессии / фиксация сессии** | `session.clear()` перед входом + новый случайный токен (`secrets.token_urlsafe(32)`), в БД хранится только sha256-хеш. Смена пароля/деактивация аннулирует все сессии. Проверено end-to-end. |
| **Подмена отчёта (business logic)** | Реализовано корректно: одноразовый токен `secrets.token_urlsafe(32)`, серверная копия raw_text, проверка `competition_id`, TTL 30 мин, флаг `used`. Позывной — строгий regex `^[A-Z0-9/]{3,20}$`, проверка «чужих связей» в логе. |
| **Утечка данных в ответах** | 429-страница статическая; ошибки плагинов выводятся только администратору. |
